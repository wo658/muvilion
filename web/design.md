# Muse interface

Muse is the starting point: one conversation, a quiet composer, and tools revealed when useful.

## Layout and copy

- Before opening a drawing, center the conversation. Use one greeting and at most two optional prompts.
- With a drawing, share the workspace between conversation and canvas. Put conversation first on narrow screens.
- No top bar. Brand, projects and settings live in one sidebar that collapses to an icon rail (collapsed by default; icons only on narrow screens).
- With a drawing, Muse is a full-height right sidebar (like the ElevenLabs agent panel) that collapses to a round launcher at the bottom right (like Channel Talk): avatar and status pill over the feed, streaming Markdown replies, ink user bubbles and a bordered composer. On phones it is a bottom sheet.
- Overview and Top fit the reviewed floor outline (or the whole drawing without one) to the actual canvas aspect and the 40° field of view with a margin, so a large hall is never cropped; a scale change refits them.
- The drawing workspace is 3D. There is no 2D/3D switch: the 2D plan appears only while a setup tool needs it (Drawing settings, crop, scale, floor outline, entrance, wall drawing) and returns to 3D when the tool closes. An unconfirmed scale keeps the 2D setup open (see Physical dimensions).
- The workspace header contains a labelled drawing selector, a direct Sources button and a separate Drawing settings icon, the Overview / Top / Explore views, and one View settings icon. On phones, wrap drawing selection/sources/drawing settings and view controls into separate rows so their hit areas never overlap. Switch drawings directly without opening source management; include PDF page numbers in drawing labels and reset the camera when changing drawings. Sources opens the source library immediately, without an intermediate menu. Planning documents belong to the References list in Sources, with their drawing names and searchable titles; the active drawing offers Create planning document when none is saved. There is no standalone planning-document header action. Drawing settings opens the 2D setup panel for scale, crop and floor outline; Sources opens its own titled view. Closing a dialog or the planning document restores focus to the persistent workspace trigger. App Settings stays separate. View settings groups cutaway, ceiling/layers, Muvi pause/hide, camera reset, and collapsed help; no standalone focus, reset, mascot or help buttons in the header.
- Sources holds up to 12 drawing sources per project. Adding a drawing preserves existing drawings; Open drawing changes the active workspace. Each drawing retains its saved geometry, scale and design edits across switches and reloads. PDF pages opened from Drawing settings are separate drawing sources and reopen their saved edits. Only the active drawing is supplied to Muse; reference materials remain shared. Undo history and unfinished dimension inputs survive switches within the session.
- Source management is a standalone Sources dialog with no drawing-settings or booth-management tabs: one search and primary Add source row, compact Drawings and References groups, small thumbnails and filenames. Add source opens a compact inline choice of drawing, concept image, brand URL or brief; choosing one closes the chooser. Avoid duplicate titles, instructional subtitles, card outlines, capacity denominators and selection toggles. Use spacing and typography instead of divider lines in the project dialog header, source chooser, brand form, removal confirmation and preview header. Every reference and the active drawing are included in Muse context automatically; legacy selection flags do not hide materials. Keep a plain current-drawing label and show page metadata only for multi-page drawings. Search only filters the visible library. Show a useful empty result and a clear-search action. Reference removal requires an inline Cancel/Remove confirmation. Brand links use an inline URL/name/notes form and explicitly remain bookmarks. Successful addition reveals the new material even when a search was active. Dialog headers remain visible while content scrolls; narrow screens wrap row actions. Preview opens from the filename row and restores focus on dismissal.
- Muse's header shows only the avatar, plus a status pill while Muse is replying; no role label. The 3D view has no floating legend or Muvi caption.
- Interior design is Muse’s primary workflow: brand references, temporary partitions, furnished booths and visitor experience. Existing-wall analysis is optional and starts only from explicit chat requests. Keep scale/floor preparation under Drawing settings.
- Proposals show the model-authored brand direction and requested deliverables linked to actual elements, separately from geometry warnings. Counts verify presence, not aesthetic quality. Never label a zone-only footprint or a concept image as a furnished interior. The run card shows them after the run; the design itself is already saved operation by operation.
- Planned schematic partition faces use their saved design color so the proposed brand palette is visible in 3D; selection and edge markers retain semantic tokens. Asset models keep authored materials.
- Remove marketing subtitles, decorative workflow steps, duplicate status copy and implementation details. Preserve actionable errors, scale warnings, review coverage and per-operation undo.
- Send is conversational. A design request builds the space directly; line review still returns a reviewable proposal that Apply changes commits. Never imply chat itself performed an edit that was not saved.

- Muse works in atomic operations (ADR-0013). Each design group (`edit_design`, at most 32 elements, for example one booth with its components) or accepted review replacement is validated on the server and committed to the project as one undo step the moment it arrives; a group that would add overlaps, out-of-floor objects or blocked circulation is rejected whole and never committed. The chat shows the saved operation count and current group label while running. In Overview and Top, the camera follows each committed operation, framing the elements it changed (at least 6 m across), and returns to the whole floor when the run completes; it never moves an Explore walk or a photo camera. A user edit to the space or a references change stops the run; cancel, failures and unmount stop it too. Saved operations always stay: the run card offers Continue design for a stopped run and Undo this design run (restores the space before the run, available while nothing else changed since). If the final reviewed revision differs from the last streamed operation it is committed as one more operation.
- Drawing reading also commits in steps: the source preview opens the drawing, then Muse's walls and its scale/floor measurement each arrive as an undo step. A later step failure keeps earlier ones; a drawing whose walls were never read shows Read again with Muse in Drawing settings. Steps merge into the drawing as it is now, so scale or floor the user set meanwhile is kept.

- Editing is conversational: no manual editing menu in the workspace header and no immediate Delete action in the selection card. Keep canvas selection, the selected-element context card, Clear selection and Ask about this. Send selected IDs and labels to intent routing, conversation and design requests; design requests are committed operation by operation. Do not show a standalone Confirm scale button in the conversation. Keep manual scale calibration in Drawing settings.

- Sample venue projects include an original fictional Meta-service planning brief, two selected brand bookmarks with authored notes, one generated exhibition-furniture concept image and one selected official article bookmark. Concept images are design inputs for Muse, clearly labelled as generated fictional concepts with provisional dimensions; they are not official products, reconstructed 3D assets or completed scene photos. Briefs are stored as UTF-8 text assets and exported with the project. Clearly label fictional planning assumptions; URLs are bookmarks, not fetched pages or official brand guidelines. Existing projects are not overwritten.
- The sample picker lists venue projects, showing included drawing names and counts. Creating a sample copies all originals and extracts the listed PDF pages into separate drawings before opening; do not create partial projects on extraction failure or silently omit missing files. The header immediately switches among the included drawings. Existing user projects are not regrouped.

- The sidebar lists projects, not legacy sample drawings. Explicitly consolidated sample projects appear once; old links open the corresponding drawing in the retained project. Preserve the old rows and originals for recovery, and reject writes from stale tabs until they reload. Independently designed projects remain separate even when they share a venue.

- App Settings uses a centered dialog and a centered content column up to 640px wide. Each section has a heading; setting rows pair left-aligned labels/descriptions with right-aligned controls. Use separators between API key actions and stack rows on narrow screens. Keep the section navigation, scrollable content and keyboard dismissal.

## Drawing import

Uploads and samples render bounded source previews in Next.js, then Meta Model reads walls and visible text. No local OCR, line detector, solver or Python service runs. Without a model key, show the source preview with an explicit no-reading warning; never imply geometry was extracted. A configured model failure is an error, not a fallback to local geometry. PDF reference pages are attached as images for Muse to read in context. Scale comes from the scale evidence Muse reports while tracing walls (ADR-0008); in parallel, Muse traces the main event floor outline and code keeps only a simple outline. Measurement failure never blocks wall reading; it leaves scale and floor to the user.

New drawings accept PDF, PNG and JPG only. The file picker and API reject DXF, with CAD-to-PDF guidance in both languages. Existing DXF projects keep their saved previews, originals and edits; do not re-render them on load. PDF coordinates follow the visible crop and rotation. Existing saved geometry/provenance is not reinterpreted on reload.

## Physical dimensions

One scene unit is one metre. Object width/depth/height are local outer bounds before rotation; rotation swaps the footprint axes, never the stored dimensions. Model objects use catalog native metre bounds (5 mm input rounding is normalized); changed proportions are rejected by design tools. A mismatched legacy asset is shown as its declared-size box with a warning, never as a silently shrunken model. Schematic fixtures use the declared assumption sizes in `lib/assets/fixtures.ts`; mesh outer bounds, 2D footprints and collision boxes share those sizes. Partitions of arbitrary length use exact schematic geometry or multiple native-size modules. Never relabel a truss as a phone stand or a coffee table as a work desk.

Real-world scale is a required setup step. A drawing without a confirmed scale (new uploads, samples and existing projects) opens Drawing settings in 2D with a Required badge and cannot close it or show the 3D workspace until scale is confirmed. Muse confirms scale when its evidence is a printed scale bar or dimension and repeated readings agree within 5%; areas and assumed module sizes stay estimates for the user to confirm. With Muse-confirmed scale the Real-world scale section then shows a Measured by Muse badge with the derived extent and evidence, and the user can re-measure at any time (their value replaces Muse's). Otherwise the user confirms the cropped drawing extent or a known measured distance (for example a scale bar). A scale confirmation establishes the coordinate conversion, not surveyed geometry. The KINTEX demo uses the printed 1B extent (90 × 63 m). The reviewed floor outline defines the entire event design area; a smaller legacy event footprint must not leave the remaining interior undesigned. Source-image margins and canvas outside that outline are not event floor. See `docs/dimensions.md` for assumptions and limits.

A new sample project whose selected sources include a brand URL or reference images is furnished once automatically: when the active drawing has confirmed scale, a floor outline and no design yet, Muse runs a whole-floor furnished interior design, committed operation by operation like any design run. The conversation says it is running. It never reruns after it has started, including after reload or failure; a stopped run offers Continue design.

Whole-space interior and zoning proposals must account for the entire reviewed floor with purposeful zones, including connected circulation and operational space. Interior proposals need actual installations in functional zones; a coloured rectangle alone is not decoration. Keep circulation clear and preserve native object dimensions. Whole-space decoration defaults to furnished interior scope; the model cannot downgrade it to zoning-only. Explicit requests for zoning alone remain supported. Designs accumulate up to the document contract’s 200 objects in groups of at most 32 edits, so larger halls are not constrained by the former 80-object proposal limit. Small targeted edits preserve unrelated design. If the floor outline is missing, request its review instead of claiming that paper margins are usable hall. Purpose-zone rectangles are clipped to the floor outline, including concave boundaries; physical installations must remain wholly inside it.

Whole-space interior completion also requires floor-level installations to span at least half of each functional zone's actual clipped width and depth. This is a product rule against tiny clusters inside oversized zones, not an occupancy, accessibility or aesthetic certification. Circulation and explicitly zoning-only proposals are exempt; the AI must still inspect the complete floor in its visual review.

In the workspace, the floor uses the indoor-floor material and a perimeter following the reviewed outline. Everything outside is a neutral canvas with a grid, visibly separate from event floor. This boundary is consistent in 2D, 3D and photography and never rescales the drawing or its objects.

## Tokens

`lib/ui/tokens.ts` owns colors. `app/layout.tsx` exposes CSS variables; `app/globals.css` maps them to Tailwind and shadcn semantic roles.

- Neutrals come from one 12-step scale (Radix Colors Slate, light) so every grey shares a hue. Keep each step in its role.
- Surfaces: `bg` (page behind panels), `surface` (sidebars, headers, panels, dialogs), `sunken` (wells, hover), `selected` (current/pressed, under `ink` or `muted` text only). Text: `ink`, `inkSoft`, `muted`; `faint` is for icons and drawing marks, never text.
- Boundaries: `hairline`, `hairlineStrong`, `edge` (outlines in drawings). Prefer subtle borders to heavy shadows.
- Actions: `accent`, `accentHover`, `accentSoft`, `accentInk`. Reserve the blue gradient (`museGlow`) for Muse's avatar.
- Status: `ok`, `bad`, `badSoft`. Overlays and shadows: `overlay`, `shadowColor`.
- Keep the existing font family, 12–14px controls, a restrained 24–32px greeting and 20px dialog/conversation corners.
- UI chrome and the 2D plan must not introduce literal colors; add a named token instead. Exhibition scene materials and the mascot are artwork and may use their own colors. `tests/tokens.test.ts` checks WCAG AA text contrast for token pairs and rejects literal colors elsewhere.
- Adding a color: name it by role in `lib/ui/tokens.ts` (camelCase; it becomes `--kebab-case`). If Tailwind classes need it, map it in the `@theme` block of `app/globals.css`. Add any new text/background pair to the contrast list in `tests/tokens.test.ts`. Remove tokens that are no longer used.
- shadcn components keep their semantic names (`primary`, `secondary`, `border`, `input`, `ring`, `destructive`), which `globals.css` aliases to Muse tokens. shadcn's `accent`/`muted` mean something else here: use `sunken`/`selected` for hover and selection backgrounds, never `bg-accent` or `bg-muted`.
- Respect reduced motion and visible keyboard focus. Dialogs require titles, Escape dismissal, close controls and focus restoration.

## Muvi mascot

Keep the rounded M silhouette, periwinkle body and dark eyes consistent across 2D and 3D. Muvi has no cheek blush; apply this to avatars, icons and the 3D model.

In the drawing space, Muvi is a small companion: cap model scale at 0.4 (about 0.85 scene units tall, roughly half an adult reference). Never enlarge it for a larger venue. Tiny spaces may shrink it further. This is a visual proportion, not an occupancy or simulation body.

## Language

Only `en` (Eng) and `ko` (한국어) are supported. App Settings changes the UI immediately; Korean is the default. The browser stores the preference and synchronizes other tabs. When storage is unavailable, the preference works for the session.

`lib/i18n/en.json` and `ko.json` are the language packs. Both must have matching keys and interpolation parameters. Use `useI18n().t()` in components and `translate()` in pure helpers. Keep full sentences together when numbers or word order differ.

Language changes preserve the conversation, composer, loaded drawing, undo history and selected sources. New Muse requests include the language enum. Historical messages, imported source text, filenames, user labels and import diagnostics remain original evidence; never silently rewrite them.

button returns to the latest message. Scrolling is instant, including reduced motion.

## Muvi motion gallery

`/muvi/gallery` is a standalone motion review page: one large orbitable preview, four selectable designer studies, pause, replay, hide and language controls. Work gestures contain no staged result geometry. Recognizable hand tools (hammer, tape measure, broad brush) and brief impact accents are encouraged; they must never imply a particular surface or completed result. Motion is deliberately cartoon-like: bold anticipation, brisk action, squash/stretch and rebound, rather than subtle physical realism. A direction control and floor marker preview their local work orientation, independent of the camera. Use broad whole-body anticipation and fast action, with trailing recovery. Feet can rock and tap within the local stage but must not penetrate the floor. The hammer and working arm rise overhead and behind the head, then swing down toward the wall while the torso gives a small backward recoil over the planted feet; it must not visibly separate from them. Hammer strikes face forward into an implied vertical wall; no wall mesh is baked in. Impact accents are bright unlit star flashes and outward-travelling diamond sparks anchored at the contact, never wooden debris or an effect dragged by the recoiling hammer. Reduced motion and hidden pages stop animation.

Designer tool operations stream as ephemeral Muvi cues: inspect, measure, arrange and paint. The agent selects a cue per grouped edit; other tools have deterministic cues. The existing reply status shows the current work gesture. Muvi pauses its illustrative patrol while working and resumes when the design ends, fails, is cancelled or the drawing/references change. Pause/hide, reduced motion and hidden-page behavior remain authoritative. Cues never claim successful construction or apply, save or export changes.

## AI photography

Chat photography requests produce a semantic shooting intent, actual 16:9 scene candidates, and an image-based model review with at most three rounds. Unsupported or unsuitable results remain errors, never approved substitutes. Photographing never changes drawing geometry. Muvi roaming, selection highlights and editor controls are excluded from photographs.

The selected photograph opens its exact camera pose and display settings in a letterboxed 16:9 viewer. Users can orbit/pan/zoom or expand fine adjustments, reopen the saved angle, retake and download the photograph. The original AI explanation describes its selected composition; a manually retaken photograph is labelled as user adjusted, not AI re-reviewed. Photos are session-only and this is stated beside download. Switching or editing drawings, changing references, cancellation and closing discard pending work. Opening a planning document from Sources opens the persistent document; standalone AI photography does not automatically create a report.

On narrow screens, photography keeps the 16:9 live frame above an independently scrolling adjustment panel. Ordinary camera presets/settings are hidden during photography on these screens; closing photography restores them.

Photography frames installed subjects by default; only an explicit whole-venue intent includes the full hall. Candidate fitting uses the actual 16:9 perspective and varies azimuth, elevation and distance. The AI reviews empty-floor proportion, subject readability and foreground obstructions; fixable issues trigger a revised angle with the original user request and previous review reason carried forward. Provisional first-shot instructions must not replace the final composition goal. An expandable composition history retains actual candidate thumbnails and each review reason for the session, including when a later round fails. Camera framing never changes the saved venue dimensions or arrangement.

Ordinary space photographs default to a visitor standing inside: 1.65 m eye height, a level horizon, moderately wide perspective, full-height walls and a solid ceiling. Where enclosure information is absent, a display-only shell follows the reviewed floor outline; it preserves evidenced wall gaps and marked entrances. Its height is estimated from the available wall height and installation tops, and the viewer labels it as partly estimated. It never writes invented walls or ceiling measurements into the source document, design checks or exports. Explore and photo capture/restoration share this enclosure. Prefer clear entrances and circulation viewpoints that reveal a meaningful activity, rather than fitting the whole hall into one image. Only the requested primary subjects are mandatory; incidental distant towers or zone edges may stay outside the frame. Image review can request substantially closer clear standing positions when subjects are too small. Eye-level candidates require a reviewed floor boundary and a clear standing position. Image-based revisions preserve this visitor perspective and move horizontally or change distance; they never silently fly upward or cut away walls. Explicit overhead/layout/elevated-detail requests retain their elevated framing.

## Seating usability

Physical object rotations support 0/90/180/270 degrees; zones retain 0/90. Fixture seating faces local -Y (north at 0°) and stores its served table/stage via useTargetId. The plan view and generated review drawings mark seat fronts. Generated seating must pass the explicit reach, pullback, legroom and connected internal approach checks in `lib/plans/usability.ts`, in addition to collision checks, before visual review/submission. Existing layouts remain readable and show localized usability issues in Items to review. Checks are concept planning allowances, not accessibility, egress or crowd certification; details and omissions are documented in `docs/dimensions.md`.

## Single design workflow and deferred platform

The current product scope is drawing and brand sources → 3D spatial design → captures and a planning PDF. Use one editor and one Muse conversation. Do not expose organizer/participant modes, actual booth sales, applications or approval controls. Planning documents may describe participation and explicitly estimated fees; this does not activate the deferred platform. A booth may still be a spatial installation in the ordinary design. Remove the separate participant implementation; former participation links redirect to the studio and former booth APIs return `410 PLATFORM_DEFERRED` without accessing legacy data. Historical booth database files remain untouched. The future platform plan does not imply active participation features.

## Persistent planning document

Opening a planning document from Sources opens a read-only Artifact in the canvas area, with the existing Muse conversation beside it. No manual title, body or price fields and no contenteditable surface. Users select a section or booth with Ask Muse about this, then request changes in the same composer. Explicit document requests update only the document; spatial edits go through Muse design runs. Questions do not mutate the document.

Store one planning document per drawing in the existing project SQLite state. It contains a source/drawing snapshot, structured narrative and booth copy, real 3D captures and up to five prior text revisions. The project's save indicator is authoritative; do not claim persistence before autosave succeeds. Reload and project export/import preserve documents and photos. Store embedded images through the existing asset table. Muvi remains excluded.

Participation inventory comes only from explicit booth/assignable zones and standalone booth installations. Dimensions derive from the saved drawing, never model-authored dimensions. Fee is an estimated participation fee, separate from construction cost, with currency, basis, inclusions and tax status. Without evidence or an explicit estimate request it is unpriced. Circulation is a plan, not simulated visitor traffic or accessibility certification. Do not invent attendance or guaranteed footfall.

Document generation and revision use Muse tool output validated against existing section and booth IDs. Preserve unrelated sections. Cancellation or stale context cannot overwrite a newer drawing/document. Captures use the existing scene renderer and photography geometry; label automatic framing for review and preserve successful text/photo results if some captures fail. Failed or unavailable photos remain visibly missing and can be requested again. Capturing must not change the user's camera or leave altered view settings.

Drawing/reference changes leave the saved Artifact readable with a stale notice. Refresh explicitly updates dimensions/references and clears old photos and incompatible text history. Preserve prose/fees for Muse review; never silently pair old photos with new geometry. Closing the Artifact does not discard it. Escape returns to space; section selection keeps the document visible and opens Muse. Narrow screens retain the existing chat sheet.

PDF is a secondary export of the saved document, including participation and photos, through the native print dialog. Wait for fonts/images, retain reprint, escape content, and never fetch bookmark URLs. The editable source of truth remains the project document, not the PDF.

## Document presentation and print pagination

Artifact navigation jumps to overview, participation and review notes without changing the selected Muse editing context. Each booth puts dimensions and estimated participation fee together above its photo, with tax status and a restrained two-column facts row. Keep complete photos letterboxed rather than cropping them; cap their display height to leave room for the accompanying information. Body text remains readable and wraps without horizontal scrolling.

A4 PDF output starts with a cover containing the title, local date, dimensions, source, overview photo and summary. Follow with design intent/circulation/operations, then each booth on a new page, optional brand references, the source drawing/installation table, and review notes. Do not repeat overview or review headings, or allocate an empty references page. Booth dimensions and fee lead each booth page; photo height is bounded so normal-length description, circulation and pricing terms stay together. Long text can continue naturally without clipping. Print page numbers and a quiet brand footer; keep snapshot identifiers in the final appendix rather than the cover.


Print design uses a quiet proposal layout: a wordmark/report masthead, a prominent balanced title, a complete overview image, and an accented summary. Narrative sections have a consistent heading/body rhythm. Booth dimensions and pricing share a shaded facts band; installation tables repeat their header and use subtle alternate rows. Korean prose keeps words together with an emergency wrap for long tokens. Use existing local system fonts and tokens; never depend on external font downloads.

The HTML/PDF design was informed by [pdf-design](https://github.com/jamditis/claude-skills-journalism/blob/master/pdf-design/SKILL.md) (cover hierarchy, brand consistency, footer clearance, rendered-page review) and [frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) (subject-specific hierarchy and restrained typography). These are design references, not runtime dependencies or copied templates. Our A4, token palette and variable-length content requirements take precedence: preserve all source text, use natural pagination, and never hide overflow or shrink the entire document to fit.

Sample creation reads drawings with Muse and may take several minutes. Show a localized reading status and an enabled Cancel preparation action while other start actions remain disabled. Cancellation aborts the request and leaves the start screen available; a late response must not open the cancelled project.

Source preview preparation also has Cancel preparation, aborts PDF page rendering on cancellation/unmount, and ignores late results without adding a source.

## Model data preference
API key settings includes a browser-scoped Contributor checkbox with explicit training-use disclosure for prompts, drawing/reference files and responses. New remote visitors default to Standard even if the developer environment uses Contributor. Loopback development retains its environment default. An explicit browser choice overrides that default, persists in an HttpOnly same-site cookie, applies to subsequent requests in all tabs, and never changes another browser or prior disclosures. This is a browser preference, not account-level isolation; shared project/key storage remains unchanged. Only supported Meta Spark 1.2/1.3 variants expose selection. Baseten, custom models and Muse Image are unchanged. Failed saves retain the previous checked state and show an error.
